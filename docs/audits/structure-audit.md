# Structure audit: the forge CLI, area boundaries and Device Lab

Reuben asked on 2026-11-19 for a deeper audit of main than individual PR reviews give: the `forge` CLI, the boundaries between the four areas ([areas.md](../areas.md)), and how Device Lab hosts the apps. The question is whether the pieces are converging or whether parallel systems are piling up. Measured at main `f5edbcf` (after #337). It changes no code and runs no builds; each finding names the smallest next step, and none of them adds a framework module or an app.

It continues the [half-baked work audit](half-baked-work-audit.md) (findings H1 to H24) and the forge-lab audit in the [App Studio spec](../research/app-studio.md) (G1 to G8). Where a finding here touches one of those, it says so and doesn't repeat it. Relay's open PRs (#339, #340) are reviewed elsewhere and not here.

**In one paragraph.** The boundaries Reuben set on 16 November hold where they are checked: no framework crate depends on tools or apps, the three listed crossings are the only ones, and CI enforces it. The problems are where nothing checks. The biggest is that native services still ship two ways: Good Dog and the starter use ForgeKit's `ForgeNative`, the other nine apps copy the same Swift into their own `Generated/` folders, so about 29,000 lines of copied Swift sit in 172 files, and the framework has grown machinery whose only job is to let those copies share one process in Device Lab (SA1, SA2). That leads to the second theme: Device Lab, the only thing that goes on the phone, proves the apps as they run together in one host, not as any of them would ship alone (SA3), and eight of the apps share a bundle id with the VPN app, so a standalone install would silently replace it (SA4). The rest is drift between lists that should be one: six places to register an app in Device Lab with one checked (SA5), three "run every check" commands that disagree (SA6), and app paths still built into the tools (SA7). One app, Weather, saves user data outside the persistence contract (SA8). After #339, the dev-connection crate has no user left in ixOS and belongs in forge-lab (SA9).

## Priorities

- **P1**: a structural problem that costs every app or risks the phone. Fix in the consolidation phase.
- **P2**: drift between lists or checks. Small, mechanical, Linux-only.
- **P3**: worth knowing; decide later or leave.

## Looked at and fine

- **Dependency direction.** No framework crate (`forge-runtime`, `forge-app`, `forge-storage`, `forge-net`, `forge-services`, `forge-native`, `forge-reader`) or ForgeKit target depends on a tool or an app, and `check-boundaries.sh` enforces it in CI. The only app names in framework code are comments.
- **Persistence layering.** `forge_app::Document` is built on `forge_storage::JsonFile`, not beside it; the duplication is in which one apps call (H10, SA9), not in the framework.
- **Headless twin tests** find every app with a `requirements.toml` by glob, so a new app can't skip them.
- **`--json`** has a versioned schema (`forge.result/1`), which is what forge-lab needs.
- **Xcode projects.** Eleven are kept for the optional macOS path. Device Lab's points at its Swift package, so it doesn't go stale as apps are added. Covering all of them is part of SA7.

1. **Protect the phone** (SA4). The install guard and the default project. Bug-fix sized, Linux-only, in the CLI.
2. **One list of checks** (SA6, SA7, SA2, SA5). One PR: `forge check` runs what CI runs, every list found by glob, the wider drift check, and the Device Lab registration check.
3. **Track the native-services route** (SA1, step 1). The parity rule with nine listed lags. Then apps move as they are touched, and phase 4 comes before any new capability.
4. **Weather's places** (SA9). One app PR, with a fixture.
5. **After #339 merges** (SA10, SA11). Move `forge-devproto` to forge-lab, bump forge-lab's pin and give it CI.
6. **Records** (SA3, SA13). "In Device Lab" on results, the 18 November sitting, and a standalone sitting in the App Store release checklist.
7. **Leave** SA8 (one help line when convenient) and SA12 (a review rule of thumb).
