# Good Dog build: ecosystem pain points

Reuben asked for a running log of friction found while building Good Dog GD1 ([good-dog-demo.md](good-dog-demo.md)), 2026-11-08. Each entry says what happened, what it cost, and a suggested fix. The build ran in a cloud session: Linux, no Darwin SDK, no iPhone. Times are wall-clock.

## Top five

1. **The SwiftUI views can't be type-checked on Linux.** `forge check swift` compiled and tested the model and bindings in 36 s, with all 6 requirements passing on the first run. But the seven view files (about 1,000 lines) were only syntax-checked (`swiftc -parse` in the Swift image). Type errors in them surface only on macOS CI or in an xtool build on the laptop. This is the biggest blind spot in a cloud build. *Fix:* type-check SwiftUI against a stub SwiftUI module on Linux (`.swiftinterface` stubs for the subset ios-ui.md recommends). Failing that, run an xtool build on the laptop automatically for each PR that touches `Sources/` (dev-loop.md gap 1, option 4).
2. **Replacing the starter is a deletion job.** `forge init` gives a notes app: about 700 lines of Rust (notes, a network check, cancellation tests) and six Swift files plus their tests, which a real app deletes on day one. The generated `README.md` and `AGENTS.md` then still name `NotesModel.swift`, `notes.add` and `uitests/smoke.toml`. *Fix:* `forge init --blank`, giving one empty `AppCore` with the lifecycle, events and logging wired, one empty screen, one model test and no notes. Write the README and AGENTS file lists from what is actually in the app.
3. **Every app hand-writes the same storage plumbing.** The starter repeats "clone the state, change it, save the file, swap it in, publish an event" in every command. Good Dog wrote it once as a `change(name, |stored| ...)` helper, and Pocket Library wraps its `JsonFile` in its own `store.rs`. *Fix:* a `forge_storage::Store<T>` holding the state, the `JsonFile`, the `EventHub` and `background`, with `read(|s| ..)` and `change(|s| ..) -> Result<T>` that saves before publishing. This is the second app to want it, so extraction is justified (rule 1).
4. **Adding an example app means editing CI in five places.** These are `rust.yml` (the cache list, Xcode project validation and a new headless-twin step), `ci-macos.sh` (the app list, the path picker and the build case) and `macos.yml` (a comment). Nothing fails if you forget one, so a new app can silently get no Swift CI. *Fix:* discover the apps (`examples/*/forge.toml`) in `ci-macos.sh` and in a single twin step that runs `forge check swift` for every app with a `requirements.toml`. Also make `scripts/check-app-crates.sh`'s auto-discovery the pattern for all of them.
5. **Test data and the clock are copy-paste.** Throwaway UI-test data (`-ForgeUITestData`, a separate folder, emptied once) is now written twice, in Pocket Library and Good Dog, almost line for line. "Now plus the phone's UTC offset", needed by any app with a "today", has no Forge type, so Good Dog added `LocalTime` and an injectable clock. *Fix:* a `ForgeTestData.directory(app:)` Swift helper next to `ForgeLog`, and a `forge_runtime::LocalTime` with a Swift `.now()` from the template. Also add a second flag that keeps test data across a relaunch, because without it a device test can't prove that data survives a relaunch (Good Dog's journey can't; only the twin test does).

## Full log

| # | Area | What happened | Cost | Suggested fix |
|---|---|---|---|---|
| 1 | `forge init` | The first run took 82 s: it compiled `uniffi-bindgen` and the app crate before writing any bindings | 1.5 min, once | Ship a prebuilt `uniffi-bindgen` with `forge`, or reuse the workspace's `target/` |
| 2 | Starter | A notes app to delete (see top five, 2). The network check, `Cancellation` and `forge-net` dependency are irrelevant to most apps | ~10 min deleting and rewriting | `forge init --blank` |
| 3 | Generated docs | The app's `README.md` and `AGENTS.md` describe the starter's files and ids, so they're wrong as soon as the starter goes | Rewrote both by hand | Generate the file tables, or keep the template's README to rules and commands only |
| 4 | Storage | Clone, save, swap and publish repeated per command (top five, 3) | ~40 lines, and the risk of forgetting to publish | `forge_storage::Store<T>` |
| 5 | Time | No local-day or clock type; every "today" feature has to invent one (top five, 5) | ~30 lines, and testability had to be designed in | `forge_runtime::LocalTime` plus a Swift `.now()` |
| 6 | Swift enums | UniFFI enums aren't `CaseIterable`, so every picker needs a hand-written `allCases` list in Swift. Adding a case in Rust won't fail the build; the picker just misses the new case | 5 hand lists to keep in step | Have `forge bindings generate` add `CaseIterable` to field-less enums (UniFFI custom config or a post-processing pass) |
| 7 | Swift error enum | `AppError` cases come out in UpperCamelCase in Swift (`.InvalidInput`), while every other enum's cases are lowerCamelCase (`.easy`) | A moment's confusion per app | Document it in ios-ui.md, or rename the cases in the bindings |
| 8 | Bundled content | Read-only content (exercises, glossary: 90 KB of JSON) has no Forge pattern. `include_str!` in Rust works but puts it in the binary, and there is no way to ship a content update without a new build | Chose `include_str!` | Document the pattern in app-crate.md. Later, a `forge-storage` "bundled resource" that reads from the app bundle, with a version check |
| 9 | Swift on Linux | Only the model and bindings compile on Linux (top five, 1). `swiftc -parse` is a free syntax check and isn't in `forge check swift` | Views unverified until CI | Add `-parse` of the view files to `forge check swift` now (cheap), type-checking later |
| 10 | Docker | `forge check swift` with `FORGE_SWIFT_DOCKER` needs a running Docker daemon. In a cloud session it wasn't running and had to be started by hand (`dockerd`) | One confusing failure | `forge check swift` could say "Docker isn't running" and how to start it, and `forge doctor` could check it |
| 11 | CI wiring | Five hand edits to add an app to CI (top five, 4) | ~10 min, easy to miss | Discover apps from `examples/*/forge.toml` |
| 12 | UI tests | An `expect` takes exactly one target, so "the row `dog.sessionsThisWeek` says 1" can't be written. `value` reads the accessibility value, which a `LabeledContent` row doesn't set | Weaker device assertion | Allow `id` plus `label_contains` in one target |
| 13 | UI tests | With throwaway test data emptied on every launch, a device test can't check that data survives a relaunch | Persistence is proven only by the twin | A second launch flag that keeps the test folder (`-ForgeUITestKeepData`), part of the helper in top five, 5 |
| 14 | Requirements | `requirements.toml` can't say "this requirement needs a device check that isn't written yet", so the journey stands in for several requirements | Coarse device evidence | Allow `device = []` with a note, or per-step evidence |
| 15 | Free team | A new demo is a new app slot (3 on a free team), so installing Good Dog means removing something from the phone first | A question for Reuben before every install | `forge device apps` showing slots and expiry (dev-loop.md fix 6), and a `forge run ios --replace <bundle id>` that removes one app on purpose |
| 16 | Workspace layout | The app crate has its own Cargo workspace but depends on `good-dog-core`, a member of the main workspace that uses `edition.workspace`. That works, but it isn't documented, and two `target/` directories build the same crate twice | Extra build time | Document "a shared core crate for an app" in app-crate.md, as Chat does with chat-core |

## What went well

- The Rust half is fast and solid: 14 app tests and 29 core tests run in under a second, and clippy and fmt are clean on the first pass.
- `forge bindings generate` took 7 s, and `scripts/check-app-crates.sh` checks fmt, clippy, tests and binding drift for the app in 15 s.
- `forge check swift` caught nothing because there was nothing to catch: all six requirement tests passed on the first run, in 36 s including the Docker image pull. That is the twin doing its job.
- The ios-ui.md conventions were clear enough to write five screens without looking at another app.
