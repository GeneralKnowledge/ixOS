# Phase 0 results (2026-11-09)

The three architecture experiments from [docs/app-model-review.md](../../docs/app-model-review.md#part-3-phased-plan), run as a strict gate before any runtime work. Everything is in this folder; CI is `.github/workflows/phase0-spike.yml` (run [42601375330](https://github.com/GeneralKnowledge/ixOS/actions/runs/42601375330), commit `0f4a7d8`, green on `ubuntu-24.04` and `macos-15`).

| Folder | What |
|---|---|
| `forge-app/` | The shared runtime contract as its own UniFFI component (`forge_app`): `AppPhase`, `ErrorKind`, `RuntimeEvent`, `RuntimeEvents`, `Cancellation`, `forge_app_contract_version()`, plus a plain-Rust `Runtime` (revision, lifecycle, events, shutdown, foreground work) |
| `ForgeKit/` | A Swift package, version 0.3.0: product `ForgeApp` (the pre-generated `forge_app` bindings) and product `ForgeKit` (`ForgeHost`, which owns the core at App level; `ForgeLifecycle` from UIApplication; `ForgeRoot`; `withRustCancellation`; errors by kind; a contract version check) |
| `SpikeApp/` | An app in the proposed shape: its Rust crate uses the `forge_app` types in its own exports and pins the framework by git commit; its own `uniffi-bindgen`; `Package.swift` depends on ForgeKit with `exact: "0.3.0"`; no copied framework files |

## What the experiments found (inputs to phase 1)

1. **UniFFI does not write the import for a second module.** The app's generated `forge_ffi.swift` uses `ForgeApp`'s converters but has no `import ForgeApp`, because UniFFI assumes one Swift module. One line added after generation (`scripts/bindings.sh`) fixes it; Forge's binding step must own that line. UniFFI 0.32 already makes the needed converters and initialisers public, and the two C modules' shared `RustBuffer` definitions did not conflict in Swift on either platform.
2. **A hidden checkout dependency in today's binding generation.** UniFFI's library mode runs `cargo metadata` in the current directory. Run from the app root (no `Cargo.toml` there), it walks up and, inside a Forge checkout, reads Forge's own workspace. Moved out of the checkout it fails. Fix: run it from `rust/`. Worth checking `scripts/generate-bindings.sh` for the same assumption when phase 3 starts.
3. **SwiftPM needs `Package.swift` at the root of a repository.** ForgeKit cannot be consumed by URL from a folder inside ixOS. CI therefore served it from a local git repository tagged 0.3.0, standing in for a real one. Phase 3 needs a decision: a separate `GeneralKnowledge/ForgeKit` repository (published from ixOS on each release), or a root `Package.swift` in ixOS. The first keeps apps' package resolution small; the second keeps one repository.
4. **The framework's Swift bindings ship pre-generated.** `forge_app.swift` is generated once per Forge version and committed in ForgeKit; UniFFI's checksums and `forge_app_contract_version()` make a mismatch between the Rust crate and ForgeKit fail at launch with a message, not misbehave.
5. **What phase 1 can generate.** The app still writes the runtime delegations (`events`, `set_phase`, `phase`, `shutdown`) and two Swift conformance lines. Both are mechanical: a Rust macro and a generated Swift file.
6. **Kept from the review's caution.** `Runtime` holds no app state and imposes no store: the spike app keeps its own `Mutex` and `JsonFile`, and the executor is not part of this spike.

## Not shown

- **xtool.** CI builds iOS with `xcodebuild`. xtool builds SwiftPM packages too, so a package dependency should work, but no xtool build of this app was run (no Darwin SDK in this session). That is the first check on the laptop, about 5 minutes, before phase 1 relies on it.
- **The phone.** No install or launch; nothing here changes the capability ledger.
- **Kotlin.** Android was not touched; `forge-app` is plain Rust apart from its UniFFI exports, so Kotlin bindings should follow, unverified.
- **A registry.** Rust used a git commit pin. `=0.3.0` from crates.io is the same guarantee and was not tried.

## xtool on Linux (Phase 1 gate, 2026-11-09)

`scripts/xtool-check.sh` on the developer laptop (Linux, xtool 1.24.0, Swift
6.2.3, Darwin SDK iPhoneOS 26.0, Rust 1.97.0), at commit 6ed61dc: `xtool dev
build` succeeded in 108 s (SwiftPM 98.7 s), with ForgeKit resolved at exact
0.3.0 from a tagged git repository. The result is an arm64 `SpikeAppXtool.app`.
Built only: nothing was installed and no phone was involved. The only output
noise was lld's usual "does not support linking for platform iOS" warnings
(11 of them).

The first run failed in the script, not the model. This SDK's configuration
prints no `toolchainPath`, and the machine has no rustup default toolchain.
The script now falls back to the clang next to `swift` (with `llvm-ar`) and
uses the app's pinned Rust toolchain.
